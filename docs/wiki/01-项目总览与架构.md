# 01 · 项目总览与架构

## 1. 项目是什么

**简卡铺**：24 小时自动发货的虚拟卡密商城（发卡站）。一套代码跑通
「浏览 → 下单 → 支付 → 自动发卡 → 查单 → 后台管理」闭环。

- 前台**不设注册登录**，客户的唯一身份是下单时填写的联系方式（手机号 / 邮箱 / QQ / 任意文本）。
- 后台是单管理员制（`admin / 123456` 演示账号），无多角色权限。

## 3. 部署拓扑

同一份后端代码按「角色」启动两个 Node 服务，**静态目录不同、API 路由相同**：

```
                ┌────────────────────────────────┐
 :2001 前台商城  │  dist/index.html      前台 SPA   │
 ─────────────► │  dist/assets/*        共享产物   │    ┌────────────────┐
                │  /admin/* ──302 跳转 → ↓        │    │  PostgreSQL     │
                └────────────────────────────────┘    │  jiankapu_dev   │
                ┌────────────────────────────────┐    │  (默认 127.0.0.1 │
 :2002 管理后台  │  dist/admin/index.html 后台 SPA │───►│   :5432)        │
 ─────────────► │  /assets/* 跨目录回落到 dist/   │    └────────────────┘
                │  SPA 回退 → index.html          │
                └────────────────────────────────┘
```

- 前端构建产物统一在 `apps/web-react/dist/`，可用 `WEB_DIST_DIR` 指到别处部署。
- 服务端向 HTML `<head>` 注入 `window.JKP_RUNTIME = { role, siteBase, adminBase }`，
  前端据此拼接跨端口绝对地址——改端口无需改前端代码。
- 不带扩展名的路径找不到文件时回退到对应应用 `index.html`（交 React Router），
  带扩展名（如 `/assets/x.js`）不回退，避免把 HTML 当 JS。

## 4. 代码分层（后端）

| 层 | 目录 | 职责 |
| --- | --- | --- |
| 入口/配置 | [src/index.js](../../apps/server/src/index.js) [src/config.js](../../apps/server/src/config.js) | 编排启动；全部可调参数 |
| 数据层 | [src/db.js](../../apps/server/src/db.js) [src/defaults.js](../../apps/server/src/defaults.js) [src/seed.js](../../apps/server/src/seed.js) | 连接池 + 事务 + 建表迁移；种子数据 |
| HTTP 层 | [src/http/](../../apps/server/src/http/) | server / router / body / respond / static |
| 工具库 | [src/lib/](../../apps/server/src/lib/) | 密码散列、二维码、支付签名、SMTP、CSV、校验等（无业务） |
| 业务层 | [src/services/](../../apps/server/src/services/) | 全部业务逻辑（纯异步函数，无 HTTP 概念） |
| 路由层 | [src/routes/](../../apps/server/src/routes/) | 薄壳：解析参数 → 调 service → 统一响应 |

调用方向严格单向：`routes → services → db/lib`，`lib` 与 `db` 之间不互调（个别服务间存在交叉调用，见 [10-依赖关系](./10-依赖关系与数据模型.md)）。

## 5. 一次完整下单的请求生命周期

```
买家浏览器(:2001)
  GET /api/public/bootstrap ─────► routes/public.js ──► category/product/settings service
  POST /api/public/orders ───────► routes/public.js ──► order.create
        └─ tx: 校验商品/规格 ► FOR UPDATE SKIP LOCKED 锁卡(未售→已锁定) ► 建订单
        └─ 事务外：payment.createPayment(订单, 渠道) ► 微信/支付宝请求 code_url
  ◄── { orderNo, qrCode(SVG data URL), expireAt } 渲染 BuyModal 二维码 + 3s 轮询
  GET /api/public/orders/:no ────► routes/public.js ──► order.findPublic
        └─ 待付款且真实渠道：payment.queryPayment 主动查单(5s 节流) ► 已付则 markPaid
  POST /pay/notify/wechat|alipay ► 回调（本地开发靠上面的主动查单兜底）
        └─ 解密/验签 ► amountMatches 核对金额 ► order.markPaid
              └─ tx: 未售卡密(已锁定→已售) + 写 order_cards ► 发卡
              └─ 事务外 fire-and-forget：notify.notifyOrderPaid(短信/邮件)
  前台轮询拿到 status=已发货 ► 展示卡密(SecretList) + 一键复制
```

## 6. 核心设计决策（详见各章）

1. **后端零 SDK 依赖**：二维码（ISO/IEC 18004）、微信 APIv3、支付宝当面付、SMTP 全部基于
   `node:crypto` / `node:net` / `node:tls` 从零实现（[04-工具库](./04-后端-工具库.md)）。
2. **SQL 写 SQLite 风格 `?` 占位符**，由 `db.js` 自动转 PostgreSQL `$1,$2`；
   事务连接用 `AsyncLocalStorage` 透传，业务层不显式传 client（[02-数据层](./02-后端-启动-配置与数据层.md)）。
3. **卡密挂在「商品 + 规格」上**（`cards.spec`），不同规格卡密池互相隔离，杜绝「买月卡发年卡」。
4. **并发安全**：锁卡用 `FOR UPDATE SKIP LOCKED`；下单/发卡/补发/退款全部走事务，失败回滚。
5. **支付安全**：回调必须验签 + 金额核对；`POST /orders/:no/pay` 手动确认仅限测试渠道（其余 409）；
   二维码有效期与本地关单时间同步。
6. **前端类型安全边界**：`shared/types.ts` 是接口契约唯一事实来源；
   `shared/api.ts` 是唯一网络出口（统一 401 处理 + `ApiError`）。
