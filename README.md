# 简卡铺 · 发卡站全栈实现

24 小时自动发货的虚拟卡密商城。**Node 后端 + PostgreSQL + React 前台商城 + React 管理后台**，一套代码跑通「浏览 → 下单 → 支付 → 自动发卡 → 查单 → 后台管理」的完整闭环。

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| 🛒 **前台商城** | **2001** | 商品浏览、下单、支付、查单 |
| ⚙️ **管理后台** | **2002** | 商品 / 订单 / 卡密 / 用户 / 设置 |
| 🗄️ **数据库** | 5432 | PostgreSQL，库名 `jiankapu_dev` |

> **前端**：React 19 + TypeScript + Vite，**严格模式类型检查零错误**。
> **后端仅一个依赖**：`pg`。支付二维码（ISO/IEC 18004）、**微信支付 APIv3**、
> **支付宝当面付**、SMTP 邮件客户端全部用 `node:crypto` / `node:net` / `node:tls` 从零实现。
> 路由、静态服务、验证码、会话、口令散列也用 Node 内置能力完成。
> **测试 188 项**：二维码规范 25 + 通知发送 13 + 接口冒烟 104 + 前端组件 46。

## 快速开始

### 1. 环境要求

- **Node.js ≥ 20**
- **PostgreSQL ≥ 12**（已在 18.6 上验证）

### 2. 创建数据库

```bash
psql -U postgres -c "CREATE DATABASE jiankapu_dev WITH ENCODING 'UTF8' TEMPLATE template0;"
```

### 3. 安装依赖

项目是 pnpm workspace，**在根目录装一次就够了**（后端 `pg` + 前端 React/Vite 全套）：

```bash
cd jiankapu

pnpm install
pnpm build        # 构建前端产物到 apps/web-react/dist

# 如果 pnpm 提示 "Ignored build scripts: esbuild"，
# 可以执行 pnpm approve-builds 放行；实测不放行也能正常构建，
# 因为平台二进制由 @esbuild/win32-x64 这个可选依赖直接提供。
```

> 用 npm 的话：`npm run setup`（等价于上面两步）

### 4. 启动

```bash
npm start
```

首次启动会**自动建表并写入演示数据**，然后访问：

| 入口 | 地址 | 账号 |
| --- | --- | --- |
| 🛒 前台商城 | http://localhost:2001/ | — |
| ⚙️ 管理后台 | http://localhost:2002/login | `admin` / `123456` |

其它命令：

```bash
npm run dev           # 后端改动自动重启
npm test              # 后端测试（自动建独立测试库，不动开发数据）
npm run test:web      # 前端组件测试
npm run test:all      # 两端全跑（100 项）
npm run build         # 重新构建前端
npm run dev:web       # 前端开发服务器（带 HMR，接口代理到 2002）
npm run reset         # 清空并重建演示数据
npm run start:site    # 只启动前台
npm run start:admin   # 只启动后台
```

> ⚠️ **前端必须先构建**：服务端只提供 `apps/web-react/dist` 里的产物。
> 没有构建过的话，访问页面会看到一个「前端还没有构建」的提示页，而不是 404。
>
> 前端改动后需要重新 `npm run build`（或开发时用 `npm run dev:web`）。
> 若把产物部署到了别处，可用 `WEB_DIST_DIR` 指向它。

## 端口与服务架构

同一份后端代码按「角色」启动两个服务，**静态目录不同，API 路由相同**：

```
                           ┌──────────────────────────────┐
   :2001  前台商城          │  dist/                       │
   ─────────────────────►  │   index.html  ← 前台 SPA      │
                           │   assets/*    ← 两者共享       │
                           │                              │
                           │  /admin/*  ──302（映射路由）─┐ │
                           └──────────────────────────────┼─┘
                                                          │
                           ┌──────────────────────────────▼─┐
   :2002  管理后台          │  dist/admin/index.html          │
   ─────────────────────►  │   后台 SPA 入口                  │
                           │   找不到的 /assets/* 回落到      │
                           │   dist/assets（跨目录回落）      │
                           └───────────┬────────────────────┘
                                       │
                           ┌───────────▼────────────────────┐
                           │   PostgreSQL · jiankapu_dev     │
                           └────────────────────────────────┘
```

**SPA 路由回退**：两个服务都开启了回退——凡是**不带扩展名**的路径（`/product/p001`、`/orders`），
找不到文件时返回对应应用的 `index.html`，交给 React Router 处理。
带扩展名的路径（`/assets/x.js`）不回退，避免把 HTML 当成 JS 返回。

**跨端口跳转**：服务端会往每个 HTML 的 `<head>` 注入
`window.JKP_RUNTIME = { role, siteBase, adminBase }`，前端据此拼接绝对地址。
所以改了端口也不用改任何前端代码。

**旧链接兼容**：`/admin`、`/admin/login.html` 这类旧地址会 302 到后台的对应 SPA 路由。

> 🔒 **生产建议**：把后台端口（2002）限制在内网或加 IP 白名单访问。

### 前台商城（2001）

### 列表操作

**排序**：点表头即可 —— 一下升序 ▲、再一下降序 ▼、第三下取消回到默认。
排序字段走服务端白名单，非法值安静回落到默认（不会报错，也不会被注入）。

**批量**：勾选后顶部出现操作条。

- 商品：批量上架 / 下架 / 删除
- 卡密：批量删除（**已售的自动跳过**，要留着跟订单对账）

批量操作是**「置为目标状态」而不是逐个切换**：勾了三个商品（两个在架一个下架）
点「批量上架」，三个都会变成上架 —— 按切换处理的话结果会跟预期完全相反。

单个商品失败**不连累其它**，失败原因会一并返回（例如「还有 2 笔待付款订单」）。

### 后台提醒

顶栏的 🔔 每 20 秒轮询一次，**前台下单立刻就能看到**：

- **新订单** → 角标数字 + 弹出 toast（`有 2 笔新订单，合计 ¥45.60`）
- **库存预警** → 铃铛红点，下拉里列出低于阈值的商品
- **已售罄** → 标红置顶，一点直达卡密页补货

「上次看到哪里」存在浏览器 `localStorage`，请求时带上 `since`，
所以**不用为已读状态建表**，多个管理员各看各的互不干扰。

> 首次打开不会把历史订单当成新订单刷屏——以当前服务器时间为基准。
> 打开下拉会把当时的事件列表**冻结**下来：否则刚点开，
> 「已读」就让后来的轮询返回空列表，你想看的内容会在眼前消失。

### 关于「客户」而不是「用户」

本站前台**没有注册登录**，所以：

- 客户的身份就是**下单时填的那个联系方式**。同一个人用同一个联系方式多次下单 = 同一个客户。
- **联系方式必填，但不限制格式**。手机号、邮箱、QQ 号、微信号、随便一句话都行。
  之所以必填，是因为它是后台识别客户、发货通知送达的唯一依据。
- **没有封禁功能**。封了也没意义——他换个联系方式照样能买。
  后台能做的是「查」：查他买过什么、从哪个 IP 买的。
  同一个联系方式被多个 IP 用过时，详情页会把所有 IP 都列出来。

### 发货通知

买家下单时**联系方式不限格式**——手机号、邮箱、QQ 号、微信号、随便一句话都能填，
后端不做任何格式校验，支付时也只认订单号。

通知按填的内容自动选渠道：

| 买家填的 | 行为 |
| --- | --- |
| `13800001111`（含 `138 0000 1111`、`+86…`） | 发货后发**短信**，内容含卡密 |
| `buyer@example.com` | 发货后发**邮件**，标题正文都可在后台改 |
| 其它任何内容 / 留空 | **不发送**，但**完全不影响下单与发货**，凭订单号仍可查单 |

配置在「系统设置 → 通知设置」：

- **邮箱**：SMTP 服务器 / 端口 / SSL / 账号 / 授权码。465 走隐式 SSL，
  587 与 25 会自动尝试 STARTTLS 升级，账号密码不会明文裸奔。
- **短信**：不绑定任何厂商，而是填一个**参数模板**：
  ```json
  {"account":"your-account","password":"{key}","mobile":"{phone}","content":"{content}"}
  ```
  `{phone}` `{content}` `{key}` 三个占位符会被替换。支持 GET / POST，
  POST 可选表单或 JSON 编码，还能设「响应体包含某段文字才算成功」。
  国内多数「账号+密码+手机号+内容」型网关（互亿无线、短信宝等）都能直接套用。
- **测试按钮**：填个邮箱或手机号点一下，**真实发一条**验证配置。
  失败时原样返回原因（如 `502 邮件发送失败：未配置 SMTP 服务器地址`），
  而不是笼统的「服务器内部错误」——否则根本没法排查是端口错了还是授权码过期了。

> 通知是「尽力而为」的：发送失败只记日志，**不会让已经完成的支付失败**。

### 后端能力

- **订单状态机**：`待付款 → 已发货 / 已关闭 / 处理中 → 已退款`
- **卡密状态机**：`未售 → 已锁定 → 已售`（订单关单自动释放回未售）
- **并发安全**：锁定卡密用 `FOR UPDATE SKIP LOCKED`，多请求同时下单不会抢到同一条
- **事务保护**：下单锁定、支付发卡、补发、退款全部走事务，失败自动回滚
- **幂等支付**：重复调用支付接口不会重复发卡
- **定时清理**：每 30 秒关闭超时订单、释放孤儿锁定、清理过期会话与验证码

## 支付

三个渠道可同时开启。**后台开了几种，前台就显示几种** —— 不看密钥有没有填全。

> ### 「已启用」和「能收款」是两件事
>
> | 状态 | 前台表现 | 能不能下单 |
> | --- | --- | --- |
> | 未启用 | 不显示 | — |
> | 已启用、密钥没填全 | **显示**，标成「暂不可用」并置灰 | 不能，服务端返回 409 |
> | 已启用、密钥填全 | 正常显示，可选中 | 能 |
>
> 之所以让没配好的也显示出来，是因为「后台明明开了、前台却找不到」最难排查；
> 而「显示了但暂时点不了」一眼就懂。后台「系统设置 → 支付设置」顶部会写明
> 前台会显示哪几种、其中哪几种买家点不了。
>
> 下单时服务端仍然会拦一道 —— 客户端判断不能当防线。
> 给买家的提示是「微信支付正在维护中，请选择其它支付方式」，
> **不会**把「缺少 AppID、商户私钥」这类内部信息抖给买家（那些只在后台和日志里）。

| 渠道 | 实现 | 需要的配置 |
| --- | --- | --- |
| **微信支付** | APIv3 Native 扫码（`/v3/pay/transactions/native`） | AppID、商户号、证书序列号、商户私钥（apiclient_key.pem）、APIv3 密钥 |
| **支付宝** | 当面付（`alipay.trade.precreate`） | AppID、应用私钥、支付宝公钥（回调验签用） |
| **测试支付** | 不联外网，点一下即成功 | 无 |

### 安全要点

- **请求签名**：微信走 `SHA256withRSA` + Authorization 头；支付宝走 RSA2 排序拼串签名。
  两边的密钥都只用 `node:crypto` 处理，没有引入任何 SDK。
- **回调验签**：支付宝用支付宝公钥验签，**验签不过一律不发货**；
  微信的金额等敏感字段是 AES-256-GCM 加密的，认证标签通过才说明来自持有 APIv3 密钥的一方。
- **金额核对**：回调与主动查单都会核对金额（`应付 vs 实付`），
  防止有人用改价工具付 1 分钱把货领走。
- **真实渠道的订单不能手动确认支付**：
  `POST /api/public/orders/:no/pay` 只对测试渠道开放，其余渠道返回 409。
  否则拿个订单号就能免费领卡。
- **二维码有效期与本地关单时间同步**（微信 `time_expire` / 支付宝 `timeout_express`），
  避免本地订单已关闭、用户却在这之后完成付款 —— 那就是「收了钱没有订单」。

### 本地开发收不到回调怎么办

网关无法回调到 `localhost`。前台轮询订单状态时，服务端会**顺带主动查单**一次
（每单最多 5 秒一次，有节流），确认已支付就照常发货。
所以本地测试真实支付也能跑通，只是到账会晚几秒。

生产环境请保证 `SITE_BASE_URL` 是公网可访问的地址，回调才能真正实时到达。

## 数据模型

13 张表：`settings` `admins` `sessions` `login_attempts` `captchas` `categories`
`announcements` `products` `cards` `orders` `order_cards` `users` `logs`

几个设计要点：

- **卡密挂在「商品 + 规格」上**（`cards.spec`），这是最要紧的一条。
  同一个商品的不同规格各自持有独立的卡密池：月卡的卡密和年卡的卡密是两批数据，
  下单时只会在所选规格的池子里取卡（`WHERE product_id = ? AND spec = ?`），
  绝不会把年卡发给买月卡的用户。没有规格的商品统一用空字符串 `''`。
- **「客户」不是注册账号，而是下单时填的联系方式**。前台没有登录，
  所以用户表里存的是「谁用这个联系方式下过单」，`last_ip` 记最近一次下单来源。
  订单详情里的 `client_ip` 才是权威来源，列表展示时优先取最新一笔订单的 IP。
  客户详情弹窗把购买记录做成卡片，上方一个**下拉框按下单 IP 筛选**（默认全部，
  选项里带每个 IP 的订单数与最近使用时间）；每条记录都能点开，
  跳到订单管理并**把那一行用橙色高亮**（不弹详情弹窗 —— 用户要的是看到它在列表里的位置）。
- **`products.stock` 是「所有规格加起来」的冗余总数**，用于列表页快速展示；
  各规格的可用数量由 `specStock` 单独返回
  （如 `{ "月卡": 12, "季卡": 0 }`），前台据此禁用售罄的规格。
  约定：`specs` 里声明的每个规格，`specStock` 里都必定有一个数字——**没有卡密就是 0**，
  而不是从结果里消失（否则前端显示不出「已售罄」）。
- **规格改名或删除会被拦下**：如果该规格下还有未售/锁定的卡密，接口直接报 409 并说明
  还剩多少条，避免卡密变成永远发不出去的孤儿数据。要改就先清空那个规格的卡密。
- **金额用 `NUMERIC(12,2)`**，连接池配了类型解析器把它转成 JS `Number`，既保证精度又不用到处 `parseFloat`。
- **`products.stock` 由 `recomputeStock()` 回写**——真实库存以 `cards` 表中
  `status='未售'` 的行数为准，避免列表查询做聚合。
- **`order_cards` 记录发出去的具体卡密**，即使卡密记录后来被删除，订单也能追溯到内容。
- **设置表是扁平 key/value**（`trade.minOrder`、`payment.wxEnable`…），
  服务层按分区聚合并做类型转换，写入走白名单校验，未知字段直接忽略。

### 库存为什么不能只按商品算

早期版本卡密只挂在商品上，于是「爱奇艺会员」的 60 条卡密混在一起：
用户买月卡，系统可能把年卡的卡密发给他。现在按规格拆分后：

```
商品 p001「爱奇艺黄金 VIP 会员」
├── 规格「月卡」 ── 55 条卡密（MONTHLY-*）
├── 规格「季卡」 ──  0 条卡密  → 前台显示「售罄」且不可选
└── 规格「年卡」 ──  5 条卡密（YEARLY-*）
```

导入卡密时**必须指定规格**，后台的卡密页会先把各规格的当前库存摊开显示，
一眼看出该给哪个规格补货。

### 从旧版本升级

`cards.spec` 是后加的列。服务启动时会自动执行幂等迁移：

```sql
ALTER TABLE cards ADD COLUMN IF NOT EXISTS spec TEXT NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS idx_cards_stock ON cards (product_id, spec, status);
```

> ⚠️ 存量卡密的 `spec` 会是空字符串，对**有规格的商品**而言这些卡密取不到，
> 相当于孤儿数据。如果是老库升级，升级后需要重新按规格导入一次卡密
> （演示数据可以直接 `npm run reset` 重建）。
>
> 另外注意：依赖新列的索引**写在迁移里而不是建表语句里**。
> `CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，
> 如果把 `CREATE INDEX ... (spec)` 放进建表语句，老库启动时会直接报
> `column "spec" does not exist`。


### 关于 SQL 写法

业务层统一写 SQLite 风格的 `?` 占位符，`db.js` 会自动转成 PostgreSQL 的 `$1,$2`。
好处是 SQL 可读性更好、迁移时业务代码几乎不用改。**请注意 SQL 里不要出现字面量 `?`。**

### 关于事务

`pg` 是异步的，事务必须用同一个连接。这里用 `AsyncLocalStorage` 把事务连接透传给所有查询，
业务层不必显式传递 client：

```js
await tx(async () => {
  const info = await run("INSERT INTO orders (...) VALUES (...) RETURNING id", ...);
  await cardService.lockForOrder(info.lastInsertRowid, productId, qty);
  // 这里所有的 get/all/run 都自动走同一个事务连接，抛错整体回滚
});
```

## 前端架构

### 为什么一个工程产出两个应用

前台和后台共用类型定义、API 客户端、设计令牌与通用组件（弹窗、分页、开关、卡密列表），
但**入口和路由完全独立**。`vite.config.ts` 里配了两个 rollup input，
一次构建分别产出 `dist/index.html` 与 `dist/admin/index.html`，
共享的 React / Router 代码被抽成公共 chunk。

| 前台路由 | 页面 | 后台路由 | 页面 |
| --- | --- | --- | --- |
| `/` | 首页（Hero + 商品网格 + 流程 + FAQ） | `/login` | 登录（SVG 验证码） |
| `/product/:id` | 商品详情 | `/` | 数据概览 |
| `/query` | 查询订单（支持 `?no=` 直查） | `/products` `/products/new` `/products/:id` | 商品管理 / 编辑 |
| | | `/categories` `/orders` `/cards` | 分类 / 订单 / 卡密 |
| | | `/users` `/settings` `/logs` | 用户 / 设置 / 日志 |

### 几个关键决策

- **`shared/types.ts` 是接口的唯一事实来源**。改后端先改这里，TypeScript 会指出所有需要同步的位置。
  例如保存设置时公告只需要 `{text, status}`，就单独定义了 `SettingsInput`，
  而不是复用带 `id` 的读取类型——这类区分能在编译期挡掉一整类字段错配。
- **`useAsync` 统一处理加载三态**：自动 `AbortController` 取消上一次请求、
  组件卸载后不再 `setState`，各页面不必各写一套 loading / error。
- **下单弹窗（`BuyModal`）承载完整支付状态机**：四步流程 + 倒计时 + 每 3 秒轮询订单状态。
  服务端下发的二维码 SVG 通过 **data URL 交给 `<img>`**，而不是 `dangerouslySetInnerHTML`，
  彻底排除 SVG 内联脚本的执行可能。
- **样式分三层**：`tokens.css`（设计令牌，改品牌色只需动 3 个变量）→
  `base.css`（前后台共用的按钮 / 表格 / 弹窗 / 表单）→ `site.css` / `admin.css`（各应用布局）。
  全部用 CSS 变量与原生嵌套的等价写法，没有引入任何 CSS 框架。
- **后台的 `api.admin.me()` 刻意不加 `silent401`**。这是之前一个真实 bug 的修复：
  加了 `silent401` 后 401 不会触发全局处理器，壳层渲染函数返回 false 却又不跳转，
  结果就是**打开后台一片空白**。现在未登录必定跳登录页，并有回归测试守着。

## 安全设计

| 项 | 做法 |
| --- | --- |
| 口令存储 | `scrypt` + 16 字节随机盐，`timingSafeEqual` 比对 |
| 会话 | 32 字节随机令牌，存服务端 `sessions` 表，HttpOnly + SameSite=Lax Cookie |
| 验证码 | 服务端生成 SVG，**一次性消费**（无论对错都删除，防枚举），5 分钟过期 |
| 登录保护 | 按 IP 计数，超阈值（默认 5 次）锁定 15 分钟 |
| 账号枚举 | 账号不存在时也执行一次假散列比对，消除响应时间差异 |
| SQL 注入 | 全部使用参数化占位符，无字符串拼接 |
| 支付密钥 | **永不回传前端**，只返回 `wxKeySet` 布尔值；提交空值表示不修改 |
| 目录穿越 | 静态服务解析后校验路径必须落在站点根目录内 |
| 请求体 | 512KB 上限，超限直接断开 |
| 越权 | 后台接口全部经 `requireAuth()`；未登录返回 401 且前端自动跳登录页 |
| 操作留痕 | 所有后台写操作写入 `logs` 表 |

## 技术说明

### 为什么后端只有一个依赖

路由、静态服务、请求体解析、验证码生成、会话管理、口令散列、二维码编码
全部用 Node 内置能力实现，唯一的第三方依赖是 PostgreSQL 客户端 `pg`。
好处很直接：**安装快、供应链风险小、没有版本冲突**。

### 二维码编码器

`src/lib/qrcode.js` 实现了 ISO/IEC 18004 的字节模式，纠错等级 M，版本 1-10：

GF(256) 伽罗华域运算 → Reed-Solomon 纠错 → 数据分块与交织 →
定位 / 校正 / 定时图形 → 8 种掩码惩罚评分选优 → 格式信息与版本信息 BCH 编码 → SVG 输出。

### 前端的类型安全边界

后端返回的是普通 JSON，前端拿到的 `any` 必须收敛。这里的分工是：

- **`shared/types.ts`** 描述接口契约，运行时**不做校验**——它保证的是「前后端字段名一致」
  和「改动可被编译器追踪」，不是安全性边界。
- **`shared/api.ts`** 是唯一的网络出口，把 `{ok:false}` 统一转成带 `code` 的 `ApiError`，
  并集中处理 401（跳登录页）与网络异常。
- 任何组件都不直接调 `fetch`。这样接口结构变化时，改动点集中且可被 `tsc` 检出。

代价是**它不防后端真的返回了错结构**。如果后端接口不稳定，
建议在 `api.ts` 的出入口加一层运行时 schema 校验（如 zod）。

### 从 SQLite 迁移到 PostgreSQL

如果想换回文件型数据库或换其它数据库，改动集中在两处：

- `src/db.js` —— 连接池、`get/all/run/tx` 四个助手的实现
- SQL 方言 —— 建表语句、`ON CONFLICT`、`FILTER`、`GREATEST`、`ILIKE` 等

`services/` 与 `routes/` 只依赖那四个助手，基本不用动。
